# WebCraft Pro v1.6.2 Release Checklist

## Release gate — carry-over items

**Definition.** A carry-over is an issue whose original target was v1.6.0
or v1.6.1 but which did not ship in that release and either remains open,
was closed after that release, or was re-targeted at v1.6.2.

**Identification (reproducible — use the primary query; fall back only if
it returns incomplete results).**

Primary:

```sh
gh issue list --state all --milestone v1.6.2 --limit 1000 --json number,title,state
gh issue list --state all --search "milestone:v1.6.0 OR milestone:v1.6.1" --limit 1000
```

Fallback — if a milestone query is unavailable or incomplete, use the
repository issues and issue-comments endpoints, which support pagination
beyond GitHub Search's 1,000-result cap. Record the tag dates and source
filters with the resulting issue links:

1. Record both release cutoffs as Unix timestamps so comparisons use
   absolute instants rather than timezone-sensitive timestamp strings:
   `git log -1 --format=%ct v1.6.0` and
   `git log -1 --format=%ct v1.6.1`.
2. Retrieve every issue page and filter locally for issues created on or
   before each release cutoff that were still open at that instant (no close
   date, or closed after the cutoff). Exclude pull requests. GitHub API
   timestamps are UTC; parse them as timestamps before comparing:
   ```sh
   V160=$(git log -1 --format=%ct v1.6.0)
   V161=$(git log -1 --format=%ct v1.6.1)
   gh api --paginate 'repos/{owner}/{repo}/issues?state=all&per_page=100' --jq --argjson cutoff "$V160" '.[] | select(.pull_request == null) | select((.created_at | fromdateiso8601) <= $cutoff and (.closed_at == null or (.closed_at | fromdateiso8601) > $cutoff)) | {number,title,state,created_at,closed_at}'
   gh api --paginate 'repos/{owner}/{repo}/issues?state=all&per_page=100' --jq --argjson cutoff "$V161" '.[] | select(.pull_request == null) | select((.created_at | fromdateiso8601) <= $cutoff and (.closed_at == null or (.closed_at | fromdateiso8601) > $cutoff)) | {number,title,state,created_at,closed_at}'
   ```
3. Retrieve all issue pages and identify issue-body deferrals independently of
   the date-based sets:
   ```sh
   gh api --paginate 'repos/{owner}/{repo}/issues?state=all&per_page=100' --jq '.[] | select(.pull_request == null) | select(.body != null and (.body | test("deferred to v1.6.2"; "i"))) | {number,title,state,body}'
   ```
4. Retrieve all issue-comment pages and identify comments that record a
   deferral to v1.6.2:
   ```sh
   gh api --paginate 'repos/{owner}/{repo}/issues/comments?per_page=100' --jq '.[] | select(.body | test("deferred to v1.6.2"; "i")) | {issue_url,created_at,body}'
   ```
   Match each comment's `issue_url` to an issue (not a pull request).
5. Reconcile the union of both date-based candidate sets, issue-body matches,
   comment matches and primary milestone queries. Inspect each candidate's
   issue body, timeline and comments for its original target release and
   whether it shipped. Record the issue number, source, original target
   release, current status, and whether it qualifies as a carry-over per the
   definition above. Record zero-result sources explicitly. Do not treat the
   manually maintained list as authoritative until every candidate from
   every source is accounted for.

**Reconciliation.**
For each identified carry-over:
- If closed, add its issue link and mark it closed.
- If still open, add a row below with a written re-deferral reason linked in
  the v1.6.2 milestone.

No implicit carry-overs. Every identified carry-over must appear below; do
not omit closed issues or open re-deferrals.
